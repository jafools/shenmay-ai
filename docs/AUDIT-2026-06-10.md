## Executive summary

**Overall health: B+.** A genuinely well-run production codebase for a tiny team — clean layering with zero circular requires, exceptional CI (5 blocking jobs per PR + a 10-cell release gate, SHA-pinned, least-privilege), a security posture that has already absorbed three deep sweeps, exemplary lockfile/license hygiene, and operational docs that survive line-by-line checks. What keeps it out of the A range is one integrity defect and two blind spots: **(1)** eight async tests in the newest, most sensitive suite are phantom passes — including the test guarding PII egress to OpenAI — so the green gates the release process leans on currently overstate what is verified; **(2)** a single unhandled promise rejection in the public Data-API auth path can crash the entire single-replica backend; **(3)** a production 500-spike is invisible today (health stays green, no error signal, no request correlation). **Top 3 risks:** false test confidence; the crash-the-backend seam compounded by observability blindness; an EOL Node 20 runtime on an internet-facing service. **Top 3 opportunities:** a half-day of test-integrity fixes that make every future green gate trustworthy; an afternoon of observability work (request IDs + a 5xx counter on `/api/health`, extending a pattern the repo already invented); and extracting `widget.js`'s duplicated session provisioning and 437-line chat orchestration, which kills the worst duplication and makes the most business-critical path unit-testable for the first time.

## Implementation sketches (top 3)

**T1 — Async-aware runner.** Collect `{name, fn}` into an array; replace inline execution with `(async () => { for (const t of tests) { try { await t.fn(); pass } catch { fail } } printSummary(); process.exit(failed ? 1 : 0) })()` — the exact shape at `tests/webhook-ssrf.test.js:39`. *Gotchas:* keep output format identical; all 8 tests should still pass (verifiers confirmed) — any failure is a *real* regression to investigate; then sweep tokenizer/openai-adapter/owner-gate for the same sync-runner-with-async-body trap.

**T4+T5 — Data-API hardening (one PR).** (1) Wrap `requireDataApiKey` in try/catch → `next(err)` (mirror `subscription.js:113`). (2) Add `process.on('unhandledRejection'|'uncaughtException')` in `index.js` — log w/ stack + structured tag, `process.exit(1)` after flush (restart policy recovers; never keep a corrupted process alive). (3) Cap-gate: rewrite the upsert as insert-gated-on-live-count à la #214; updates of *existing* externals must still succeed at cap (try UPDATE by (tenant, external_id) first, fall through to cap-gated INSERT). *Gotchas:* keep the anon-email exclusion consistent with the widget's count; add integration tests for at-cap create vs. at-cap update; document the new 403 in `docs/DATA-API.md`.

**T10 — Observability.** (1) `requestId` middleware: `crypto.randomUUID()` → `req.id` + `X-Request-Id` header. (2) pino base logger; the request logger now fires at *finish* with status+latency+id+tenant; leave the 227 console calls for incremental migration (new code uses the logger). (3) 5xx counter via a response-finish hook (`res.on('finish', …)`), **not** the error handler — 12 route-level `res.status(500)`s bypass it — exposed as `http_5xx_total` on `/api/health`, mirroring `audit_write_failures`. (4) Sentry guarded by `SENTRY_DSN` so self-hosted stays silent by default. *Gotchas:* skip `/api/health` in the request logger; add the new env vars to `.env.example` **and** both compose files (the env-forwarding lint will catch omissions).
